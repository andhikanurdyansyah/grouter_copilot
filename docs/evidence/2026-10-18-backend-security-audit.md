# Defect Register — Audit Backend & Keamanan gRouter Copilot (READ-ONLY)

- **Tanggal:** 2026-10-18 · **Scope:** `server/src/{server,auth,settings,store,notifications,mail,paymentService,licenseService,accountService,klikqris,gateway,usageResolver,usageReconciliation,readiness,frontend,frontendServer,loadEnv,loadKeys,index}.js`, `server/src/entitlement.js`, `src/license/validate.js` (mint), `src/adapter/grouter.js` (jalur error gateway), `frontendServer` proxy 4601→4600, store prod dibaca read-only (tanpa nilai kredensial/token).
- **Metode:** baca penuh semua file di scope (4.959 baris `server/src` + dependensi jalur), inventaris endpoint × auth, probe runtime hanya pada file temp di `/tmp` (store korup, cek pola kode). Server prod **tidak** diboot, data prod **tidak** dimutasi, kredensial **tidak** dicetak.
- **Di luar temuan (sudah selesai, tidak diaudit ulang per brief):** engine notifikasi D-022 + reliability hardening; trust model webhook KlikQRIS (re-verify upstream, `SUCCESS|PAID|SETTLEMENT`); harga order server-side dari plan catalogue. **Tidak ditemukan defect BARU yang konkret pada ketiga area itu** — kecuali A-09 yang bersinggungan dengan settlement dan dicatat dengan bukti test yang ada.
- **Ringkasan:** 0×P0 · 3×P1 · 7×P2 · 7×P3. Tidak ada endpoint admin tanpa `requireAdmin`, tidak ada IDOR lintas akun yang terbukti pada endpoint customer, tidak ada kebocoran kredensial provider di response customer. Risiko terbesar bersifat **integritas/durabilitas data** (store JSON) dan **fail-open senyap** (settings/auth), bukan RCE atau bypass auth langsung.

**Severity:** P0 = eksploitasi aktif / kehilangan uang-data sekarang · P1 = jalur eksploitasi atau kehilangan data yang realistis, perbaiki sebelum scale · P2 = defect konkret dengan dampak terbatas / prasyarat khusus · P3 = hardening / hygiene.

## A. Temuan

### A-01 · P1 · Korupsi parsial store.json → wipe senyap seluruh store, lalu persist permanen
- **Lokasi:** `server/src/store.js:43-63` (`_load`, `catch { return empty }`), dipicu tulis pertama di `store.js:339-344`, `store.js:97` dst.
- **Skenario reproduksi (terverifikasi dengan probe di `/tmp`):** tulis `{corrupt!!!` ke file temp → `new JsonStore()` memuat `licenses=0, accounts=0`; `_save()` pertama (mutasi apa pun: heartbeat, order, notifikasi) menimpa file dengan state kosong + satu record baru. Di prod: crash/power-loss di tengah `writeFileSync` file 149 KB (rename memang atomik, tapi file `.tmp` yang tertulis parsial + rename yang tidak ter-fsync bisa menghasilkan file target terpotong di filesystem tertentu), atau edit manual yang salah → restart berikutnya memuat store kosong **tanpa alarm apa pun**, dan mutasi pertama mengunci kehilangan itu secara permanen. Tidak ada backup, tidak ada checksum, tidak ada log.
- **Akar masalah:** kegagalan parse diperlakukan identik dengan "file belum ada". Tidak ada fallback `.bak`, tidak ada `fsync` sebelum/sesudah rename, tidak ada validasi skema hasil parse (array bisa berisi `null` → crash tersebar belakangan).
- **Saran fix:** (1) bedakan ENOENT dari parse-error: parse-error → throw saat boot (fail-loud) atau muat `store.json.bak` terakhir-valid; (2) tulis `.tmp` → `fsyncSync(fd)` → rename → fsync direktori; (3) rotasi backup (`store.json.bak` = salinan valid terakhir sebelum overwrite); (4) validasi bentuk minimal hasil parse (semua koleksi adalah array, settings adalah object) sebelum diterima.

### A-02 · P1 · Store file world-readable berisi token lisensi bertanda tangan + kredensial per-lisensi legacy
- **Lokasi:** `server/data/store.json` mode `644 root:root` (terverifikasi `stat`), isi record di `server/src/licenseService.js:35-51` (`token`, `grouterApiKey`), tulis tanpa mode eksplisit di `store.js:342`.
- **Skenario:** pengguna lokal non-root mana pun di host (atau proses lain yang terkompromi dengan user berbeda) membaca `/home/ubuntu/grouter_copilot/server/data/store.json` → memperoleh **seluruh token lisensi pelanggan yang masih berlaku** (`record.token` dipersist demi fitur recovery) → memakai gateway AI atas kuota korban via `POST /api/copilot/chat {token}` sampai kuota habis, dan `grouterApiKey` legacy bila terisi. Bandingkan: `server/.env` dan `auth.sqlite` sudah `600`, direktori `data/` sudah `700` — justru file dengan konsentrasi rahasia tertinggi yang tertinggal `644` (umask default pada `writeFileSync`+`rename`, file baru mewarisi mode temp).
- **Akar masalah:** `_save()` tidak pernah menetapkan mode; tidak ada pertahanan berlapis bila permission direktori berubah/di-copy keluar (backup, rsync, tar).
- **Saran fix:** `writeFileSync(tmp, ..., { mode: 0o600 })`; `chmod 600` file eksisting; pertimbangkan memisahkan `token` ke koleksi terpisah atau mengenkripsi at-rest; audit skrip backup agar tidak memperlebar ACL.

### A-03 · P1 · SSOT config drift: pengaturan admin mengklaim mengendalikan perilaku yang sebenarnya hanya dibaca sekali saat boot (atau dari env saja)
- **Lokasi:** boot-time singleton `server/src/auth.js:93` (`resolveSettings({}, process.env)` — store sengaja tidak dibaca), `server/src/server.js:239-264` (`usage`, `klikqris` dibangun sekali dari `effSettings` saat boot), `server/src/gateway.js:315-331` (`createGateway` mem-freeze `adapter.baseUrl/timeoutMs/gatewayConfig` + `env.GROUTER_API_KEY` saat konstruksi, hanya `policy/plans` yang live via `resolveSettings` per request di `gateway.js:112,132`), `server/src/index.js:31-34` (readiness membaca `KLIKQRIS_MODE` dari env, bukan settings efektif), `server/src/server.js:673` (`GROUTER_API_KEY` env murni — by design D-021, tapi tidak terdokumentasi di UI settings).
- **Skenario:** admin mengubah `payment.mode` sandbox→production, `payment.apiKey`/`merchantId`, `provider.baseUrl`, `provider.gateway.*`, `usage.checkUsageUrl/cacheTtlMs`, atau seluruh `auth.*` (termasuk `trustedOrigins`, `minPasswordLength`, threshold sentinel) lewat `PATCH /api/admin/settings` → `GET /api/admin/settings` menampilkan nilai baru sebagai efektif → **perilaku runtime tidak berubah sama sekali** sampai `pm2 restart`. Kasus terburuk: operator mengira pembayaran sudah production (atau sebaliknya: mengira masih sandbox saat sebenarnya env berkata production), atau rotasi `trustedOrigins`/kredensial pembayaran "sudah diterapkan" padahal belum. Komentar di `auth.js:88-92` mengakui untuk auth, tetapi kontraknya tidak ditegakkan di UI/respons PATCH.
- **Akar masalah:** dua kelas pengaturan (hot vs boot-only) dicampur dalam satu permukaan tulis tanpa metadata `requiresRestart`, sementara beberapa service meng-cache resolusi saat konstruksi.
- **Saran fix:** tandai section boot-only di `validateSettings`/respons PATCH (`{ settings, requiresRestart: ['auth','payment.credentials','provider.baseUrl', ...] }`); konstruksi ulang `klikqris`/`usage`/gateway-config per request dari `resolveSettings(store.getSettings())` (murah: objek ringan, fetch diinjeksikan) atau baca dinamis seperti `notificationService.settingsGetter`; readiness memakai `paymentMode` efektif, bukan env.

### A-04 · P2 · Endpoint customer & admin tanpa rate-limit: pemulihan token lisensi, ekspor CSV, order create/cancel, baca order
- **Lokasi:** peta limit hanya 4 path di `server/src/server.js:149-154`; tanpa limit: `GET /api/me/licenses` + `GET /api/me/licenses/:id/token` (`server.js:973-1009`), `GET /api/me/usage/export` + `GET /api/me/orders/export` (`server.js:883-905`), `POST /api/orders` (`server.js:1126-1163`, setiap panggilan = panggilan berbayar-sisi-provider `createQris`), `POST /api/orders/:id/cancel`, `GET /api/orders/:id`, dan seluruh `GET/PATCH /api/admin/*` di belakang satu token statis.
- **Skenario:** (a) sesi customer yang terkompromi (XSS/storage theft di origin yang sama, perangkat bersama) mengunduh token lisensi berulang tanpa gesekan — token adalah bearer credential AI; tidak ada audit log/revoke-otomatis pada recovery, dan token yang sama tetap valid setelah "recovery". (b) Skrip dengan sesi valid meng-`POST /api/orders` ribuan kali → ribuan QRIS intent di provider + baris order tak terbatas (lihat A-08) → noise rekonsiliasi & potensi biaya/rate-limit provider. (c) Brute-force `ADMIN_TOKEN` online tanpa limiter di lapisan app (bergantung penuh pada Cloudflare/sentinel yang tidak mencakup token Bearer custom ini); token adalah satu-satunya kunci seluruh operasi admin (issue/revoke/settings berisi kredensial pembayaran).
- **Akar masalah:** `RATE_LIMITS` hanya menarget "unauthenticated license-exchange surfaces"; permukaan authenticated dianggap aman karena sesi, tanpa mempertimbangkan sesi curian dan tanpa limit biaya per akun.
- **Saran fix:** limiter per-akun (bukan hanya per-IP) untuk token recovery/export/order-create (mis. recovery 10/jam/akun, order-create 10/menit/akun, export 5/jam/akun); limiter per-IP global untuk `/api/admin/*`; log peristiwa recovery (accountId, licenseId, waktu — tanpa token).

### A-05 · P2 · `/api/copilot/chat`: rate-limit dihitung dua kali, dan limit per-IP tak berguna di belakang proxy satu-hop
- **Lokasi:** `server/src/server.js:313` (pre-dispatch, semua path di `RATE_LIMITS`) + `server/src/server.js:560-562` (khusus chat di dalam handler), kunci `req.socket.remoteAddress` di `server.js:158,313,560`; proxy meneruskan header apa adanya di `server/src/frontendServer.js:264-288` tanpa menormalkan IP; bandingkan auth yang benar di `auth.js:214-223` (`cf-connecting-ip` + `trustedProxies` loopback).
- **Skenario:** produksi single-origin: semua request chat tiba dari `127.0.0.1` (frontendServer 4601) atau dari cloudflared → satu bucket bersama **60/menit untuk seluruh pelanggan** → pelanggan sah saling men-starve (DoS kolektif saat >60 chat/menit agregat), sementara penyerang langsung ke port 4600 (bila terekspos) mendapat bucket sendiri per IP. Double-count: request chat mengonsumsi 2 hit (pre-dispatch + in-handler dengan kunci bucket yang sama persis), jadi batas efektif chat adalah ~30/menit/bucket, bukan 60 yang tertulis. Hal yang sama berlaku untuk `/api/resolve` + `/api/heartbeat` yang berbagi socket-IP proxy.
- **Akar masalah:** limiter memakai alamat soket transport, bukan identitas klien tepercaya; registrasi ganda untuk chat tertinggal dari dua lapisan pertahanan yang ditambahkan terpisah.
- **Saran fix:** turunkan kunci dari rantai header tepercaya yang sama dengan Better Auth (`cf-connecting-ip` bila peer adalah loopback/proxy tepercaya, fallback socket), hapus salah satu dari dua pemanggilan untuk chat (pertahankan in-handler), dan pertimbangkan limit kedua per-licenseId (token sudah divalidasi di gateway — limiter berbasis lic akan jauh lebih tepat untuk permukaan berbayar ini).

### A-06 · P2 · `settlePaid` non-atomik: draf lisensi yatim / risiko dobel-terbit berada satu `await` dari kenyataan
- **Lokasi:** `server/src/paymentService.js:76-105` — cek `status === 'PAID'` sinkron, `licenseService.issue()` sinkron (`licenseService.js:53` → `store._save()`), lalu mutasi `order.status='PAID'` + `store._save()`; webhook di `server.js:1215` dan settle admin di `server.js:1103-1116` sama-sama `await` sebelum memanggilnya.
- **Catatan kalibrasi (jujur):** dalam topology **satu proses hari ini**, tidak ada `await` antara cek dan kedua `_save()`, jadi event loop membuat urutan ini atomik — dan memang ada test lulus `payment-safety-gaps.test.js:49` (8 webhook konkuren → tepat 1 lisensi). Klaim "race dobel-terbit sekarang" akan salah. Defect-nya adalah kerapuhan struktural + satu jalur yatim yang nyata hari ini:
  - **Lisensi yatim (terjadi sekarang):** `issue()` berhasil ter-save, lalu proses mati sebelum baris `order._save()` berikutnya (masih di tick yang sama — jendelanya kecil tapi bukan nol: kill -9/OM di antara dua `writeFileSync` 149 KB), atau `_save()` kedua gagal (disk penuh) → lisensi aktif ada untuk order yang selamanya `PENDING`. Webhook retry berikutnya menerbitkan **lisensi kedua** (idempotensi hanya melihat `order.status`), order menunjuk yang kedua, yang pertama tetap valid & tak tertaut — kuota ganda untuk satu pembayaran. Jalur sebaliknya aman by design (gagal issue → tetap PENDING).
  - **Satu refactor dari dobel-terbit:** `settlePaid` dideklarasikan `async`; penambahan `await` tunggal di masa depan (mis. kirim email di dalam settle, ambil settings dari jaringan) di antara cek dan mutasi membuka race antar-request yang test konkuren di atas akan langsung gagalkan — tidak ada pengaman (kunci per-order / status transisi `SETTLING`) yang menjaga invariant ini.
- **Saran fix:** transisi status dua fase dalam satu `_save()`: tulis order `PAID + licenseId` **bersama** record lisensi dalam satu mutasi store (satu `addLicense` + mutasi order sebelum `_save()` yang sama — refactor `issue()` agar bisa defer save), atau status antara `SETTLING` yang membuat pemanggil kedua menunggu/menyerah; tambah test disk-failure di antara kedua save.

### A-07 · P2 · `mintLicense`: payload menimpa `iat`/`exp` — token tanpa kedaluwarsa dapat diterbitkan oleh pemanggil yang lalai
- **Lokasi:** `src/license/validate.js:46-50` — `{ iat: notBefore ?? now, exp: expiresAt ?? now+365d, ...payload }`: spread payload **setelah** klaim terdaftar, sehingga `payload.exp`/`payload.iat` apa pun menang; `validateLicense` di `validate.js:88` memperlakukan `payload.exp` absen sebagai tidak pernah kedaluwarsa.
- **Skenario:** hari ini satu-satunya pemanggil server adalah `licenseService.js:28-33` (payload bersih: `aud/lic/customer/features/quota`), jadi belum tereksploitasi. Tetapi `mintLicense` diekspor publik dari paket (`src/index.js:12`) dan dipakai plugin/test; perubahan mendatang yang meneruskan objek longgar (mis. `mintLicense({ payload: body })` atau plan JSON dari settings yang membawa field `exp` dalam detik vs milidetik — perangkap satuan yang sudah ada: `licenseService` menggandakan `expiresAt * 1000` di satu jalur) dapat menerbitkan token yang tidak pernah kedaluwarsa atau langsung kedaluwarsa, tanpa error. Ini adalah satu-satunya jalur penerbitan kredensial jangka panjang; fail-unsafe di sini mahal.
- **Akar masalah:** urutan spread terbalik untuk klaim keamanan + `exp` opsional di validator untuk token yang diterbitkan server.
- **Saran fix:** klaim terdaftar terakhir: `{ ...payload, iat, exp, nbf? }` (dan tolak payload yang memuat `exp/iat/nbf/aud/lic`); atau validator server-side mode ketat yang mewajibkan `exp` numerik. Tambahkan test regresi "payload dengan exp jahat diabaikan/ditolak".

### A-08 · P2 · Pertumbuhan store tak terbatas: `orders`, `usage`, `heartbeats` tanpa retensi; `_save()` menulis ulang seluruh file di setiap mutasi
- **Lokasi:** `server/src/store.js:388-392,418-422,460-472` (append tanpa trim; bandingkan notifikasi yang dibatasi di `store.js:90-96,260-264`), tulis penuh di `store.js:339-344`.
- **Skenario:** setiap chat gateway = 2× tulis penuh file (reserve + reconcile), setiap heartbeat/order menambah baris selamanya. File prod saat ini 149 KB / 185 baris usage — sehat, tetapi lintasan pertumbuhannya linear tanpa plafon: pada 100 ribu baris usage, setiap chat menulis ulang file multi-MB secara sinkron di event loop → latensi semua endpoint naik bersama, jendela korupsi A-01 melebar, dan restart memuat semuanya ke memori. Digabung A-04(b): order PENDING spam mempercepatnya dari sisi penyerang.
- **Akar masalah:** JSON-store adalah pilihan sadar (zero-dependency), tetapi kebijakan retensi hanya diterapkan pada notifikasi.
- **Saran fix:** plafon per koleksi (usage: retensi hari/jumlah dengan ringkasan agregat yang dipertahankan untuk `usageTotals` seumur lisensi — hati-hati: kuota adalah lifetime, jadi arsipkan total per lisensi sebelum memangkas baris); heartbeats cukup simpan per (license,install) terakhir; pertimbangkan append-only journal / SQLite sejajar auth bila lintasan pertumbuhan menuntut.

### A-09 · P2 · Kesalahan validasi settings tertentu bocor sebagai HTTP 500 + pesan internal
- **Lokasi:** `server/src/server.js:768-770` — `sendJson(res, err.code === 'INVALID_SETTINGS' ? 400 : 500, { error: err.message })`; jalur lempar non-`INVALID_SETTINGS` dari `stripMaskedSecrets`/`deepMerge` (mis. `clone()` = `JSON.parse(JSON.stringify(v))` pada nilai siklik dari body JSON tidak mungkin siklik, namun `validateSettings` sendiri melempar `fail()` ber-code — jalur 500 terutama dari `store.updateSettings`/`resolveSettings`).
- **Skenario:** admin terautentikasi mengirim patch yang lolos `validateSettings` tetapi meledak di `updateSettings`/re-resolve (mis. bentuk plans yang valid per-validator tetapi memicu asumsi di `resolvePlanAiPolicy` saat resolve ulang) → respons `500 {error: "<pesan internal Node>"}` membedakan kegagalan server dari kesalahan pengguna dan membocorkan detail implementasi kepada pemegang token (dampak rendah karena sudah admin, tetapi mengacaukan kontrak API dan menyulitkan diagnosis UI: UI menelanjangi semua 500 sebagai "gagal simpan").
- **Akar masalah:** satu `catch` untuk tiga fase (validasi, persist, resolve) dengan pemetaan status berdasarkan `err.code` yang hanya dimiliki fase pertama.
- **Saran fix:** bungkus fase secara terpisah: validasi → 400 selalu; persist/resolve → `500 {error: 'settings could not be saved'}` + log server-side berisi pesan asli.

### A-10 · P2 · `/api/orders/latest` menautkan lisensi ke order berdasarkan heuristik waktu, bukan `order.licenseId`
- **Lokasi:** `server/src/server.js:949-954` — memilih lisensi milik akun dengan `createdAt >= order.createdAt` terbaru, mengabaikan `order.licenseId` yang sudah dipersist settlement (`paymentService.js:101`, dibaca dengan benar oleh receipt di `server.js:1047`) dan dijamin cocok dengan akun (terverifikasi pada 2 order PAID prod: tautan `licenseId` konsisten).
- **Skenario:** akun membeli paket A (order terbaru), lalu menerima lisensi lain sesudahnya (penerbitan admin, pembelian kedua yang settle lebih dulu karena webhook terlambat, renewal manual) → halaman `/success` menampilkan **token lisensi yang salah** kepada pelanggan ("lisensi Anda") padahal lisensi dari pembayaran ini adalah yang lain. Bukan IDOR (keduanya milik akun yang sama — batas kepemilikan dipatuhi), tetapi kesalahan integritas customer-facing: pelanggan menginstal token yang salah, dukungan men-debug "lisensi tidak aktif", dan dalam kasus renewal perpanjangan yang dimaksud tidak terpakai.
- **Akar masalah:** heuristik pra-`licenseId` tidak diganti setelah settlement mempersist tautan otoritatif.
- **Saran fix:** `const license = order.licenseId ? store.getLicense(order.licenseId) : <heuristik lama sebagai fallback>` + verifikasi `license.accountId === account.id`.

### A-11 · P3 · Perbandingan token admin tidak konstan-waktu; satu token statis tanpa rotasi/revokasi per-operator
- **Lokasi:** `server/src/server.js:1283-1292` (`auth === \`Bearer ${adminToken}\``, tanpa `crypto.timingSafeEqual`).
- **Skenario:** timing side-channel terhadap perbandingan string Bearer melalui jaringan bising secara praktis tidak realistis dieksploitasi per-karakter, dicatat sebagai hygiene: token tunggal bersama berarti kebocoran satu operator = seluruh permukaan admin (termasuk menulis kredensial pembayaran via settings), tanpa atribusi audit. Token juga disimpan browser di `sessionStorage` (`frontend/src/features/shared/admin-auth.ts:9-16`) — dapat dibaca skrip apa pun di origin (lihat konteks A-16: permukaan XSS klasik masih hidup).
- **Saran fix:** `timingSafeEqual` atas hash kedua sisi; pertimbangkan token per-operator atau setidaknya log penggunaan admin (endpoint + waktu, tanpa token); rotasi terdokumentasi.

### A-12 · P3 · Gateway: dua cabang `NOT_CONFIGURED` menulis ke record usage yang tidak pernah dibuat
- **Lokasi:** `server/src/gateway.js:161` dan `gateway.js:184-190` memakai `store.updateUsageRecord(requestId, ...)` padahal tidak ada `addUsageRecord` sebelumnya pada kedua jalur itu (bandingkan cabang tetangga `gateway.js:144,155,171,204` yang benar memakai `_ledgerEntry` + `addUsageRecord`); `updateUsageRecord` no-op senyap pada id tak dikenal (`store.js:424-430`).
- **Dampak:** penolakan karena provider non-grouter / model tak terpakai tidak meninggalkan jejak ledger apa pun — admin ledger (`/api/admin/ledger`) tidak dapat membedakan "tidak pernah meminta" dari "ditolak karena konfigurasi", melemahkan audit tagihan & debugging. Fungsional ke pelanggan tetap benar (respons `NOT_CONFIGURED` terkirim).
- **Fix:** ganti keduanya menjadi `addUsageRecord(this._ledgerEntry({ requestId, lic, status: 'rejected', errorClassification: 'not_configured' }))` (sesuai pola cabang lain).

### A-13 · P3 · Idempotensi gateway tidak pernah mengembalikan jawaban tersimpan (fitur rusak senyap; untungnya bukan kebocoran)
- **Lokasi:** `server/src/gateway.js:110-120` membaca `existing.answer`; keberhasilan menulis hasil di `gateway.js:220-230` **tidak** menyertakan `answer` (terverifikasi probe pola: field tidak pernah ditulis; 185 baris usage prod semua `answer: null`), padahal `_ledgerEntry` menyiapkan `answer: null` (`gateway.js:300`).
- **Dampak:** retry dengan `requestId` sama setelah sukses menerima `answer: ''` (string kosong berstatus `ok`/`partial`) — pemanggil mengira jawaban kosong adalah jawaban asli. Integritas respons, bukan keamanan; dan keputusan untuk **tidak** mempersist jawaban sebenarnya baik dari sisi privasi (prompt/jawaban tidak disimpan) — perilaku replay-lah yang harus jujur.
- **Fix:** pilih satu: persist `answer` terenkripsi/terbatas + sadari implikasi privasinya, **atau** (disarankan) replay mengembalikan `code: 'REQUEST_ALREADY_COMPLETED'` tanpa jawaban palsu, sesuai cabang non-ok di `gateway.js:122-126`.

### A-14 · P3 · Konfigurasi sesi Better Auth tidak dinyatakan: mengandalkan default library yang tidak ter-pin di repo
- **Lokasi:** `server/src/auth.js:126-236` — tidak ada blok `session` (`expiresIn`/`updateAge`/`cookieCache`), tidak ada `account`/`user` hardening eksplisit; plugin `organization()` aktif (`auth.js:165`) tanpa permukaan produk yang memakainya (frontend hanya menampilkan label organisasi statis).
- **Dampak:** umur sesi efektif = default Better Auth 1.x (7 hari, diperpanjang saat aktivitas) — masuk akal, tetapi tidak pernah diputuskan/didokumentasikan untuk produk berlisensi berbayar; `organization()` memperluas permukaan API `/api/auth/organization/*` (buat org, undang anggota) yang dapat dipakai pengguna terautentikasi mana pun tanpa nilai produk saat ini, masing-masing dengan asumsi otorisasi plugin yang tidak diaudit di repo ini. Sentinel/dash aktif hanya bila `BETTER_AUTH_API_KEY` terisi (readiness menandainya advisory, `readiness.js:41-50`).
- **Fix:** nyatakan `session: { expiresIn: ..., updateAge: ... }` secara eksplisit sesuai keputusan produk; nonaktifkan `organization()` sampai ada kebutuhan multi-tenant nyata, atau audit & uji jalurnya; pertimbangkan menjadikan `better-auth-api-key` blocking untuk go-live.

### A-15 · P3 · `ensureAccount` menautkan akun berdasarkan email tanpa memverifikasi kepemilikan penghubung
- **Lokasi:** `server/src/accountService.js:17-41` — akun store dicari dengan `getAccountByEmail(user.email)` (`store.js:364-366`, pencocokan persis, case-sensitive); `authUserId` ditautkan hanya bila kosong, tidak pernah dikoreksi bila berbeda.
- **Skenario:** umumnya aman karena Better Auth memverifikasi email via password/Google. Sisa risiko: (a) dua identitas auth dengan email sama yang berbeda kapitalisasi/penyedia menghasilkan dua akun store terpisah (atau sebaliknya tertaut ke akun yang salah bila email didaur ulang penyedia) — lisensi "hilang" dari dashboard adalah kegagalan integritas yang akan terlihat seperti IDOR oleh pelanggan; (b) `user.email` kosong dari penyedia → akun dengan email `''` yang dapat tertaut silang pada pemanggilan berikutnya dengan email kosong. Belum ada bukti kejadian di data prod (3 akun konsisten).
- **Fix:** normalisasi email (lowercase/trim) di satu tempat; tautkan berdasarkan `authUserId` terlebih dahulu, email sebagai fallback; tolak `ensureAccount` tanpa email terverifikasi.

### A-16 · P3 · Permukaan XSS klasik masih disajikan (dashboard fallback menginjeksikan JSON ke HTML) berdampingan dengan SPA
- **Lokasi:** `server/src/server.js:1332-1339` (`renderDashboardHtml` mengganti `__STATS_JSON__`/`__LICENSES_JSON__` dengan `JSON.stringify` ke template HTML — aman hanya selama template membungkusnya bukan di konteks `<script>` mentah tanpa escaping `</script>`; `JSON.stringify` tidak meng-escape `/`), rute fallback di `server.js:362-366` dan `frontendServer.js:250-257`; CSP backend tidak diset sama sekali (hanya 4 header di `server.js:306-309`; CSP lengkap hanya di frontendServer `frontendServer.js:68-83` yang tidak berlaku untuk respons yang disajikan langsung port 4600 bila terekspos).
- **Skenario:** nama customer yang dikendalikan penyerang (via penerbitan admin tidak, tetapi `customer` pada lisensi berasal dari `order.planName`/input admin) memuat `</script><script>…` → bila fallback klasik ter-render (build SPA absen), token admin di `sessionStorage` origin yang sama tereksfiltrasi. Prasyarat berlapis (SPA absen + akses langsung 4600 + nama jahat) membuat ini P3, bukan P1.
- **Fix:** escape `<` sebagai `\u003c` pada JSON yang diinjeksikan (atau hapus fallback klasik); samakan CSP untuk port 4600; jangka panjang: pindahkan token admin keluar dari jangkauan JS (cookie httpOnly via backend session admin) — perubahan besar, cukup dicatat.

### A-17 · P3 · `/api/config` mengiklankan `payment.enabled` dari objek KlikQRIS boot-time (drift turunan A-03) + `/api/health` tidak memeriksa jalur tulis store
- **Lokasi:** `server/src/server.js:723-741` (`klikqris.configured/mode` dari konstruksi boot; mengubah kredensial via settings tidak mengubah jawaban sampai restart — UI checkout dapat menyembunyikan pembayaran yang sebenarnya siap, atau sebaliknya), `server.js:690-720` (health hanya `Array.isArray(store.listLicenses())` — lolos saat disk penuh/read-only, ketika setiap mutasi `_save()` akan throw di tengah request; probes L8 diarahkan di luar scope file ini tetapi kontrak health-nya di sini).
- **Fix:** resolusi `configured/mode` per request dari settings efektif; health menyertakan probe tulis-temp yang murah atau setidaknya `accessSync(W_OK)` pada direktori data.

## B. Area yang diperiksa dan bersih (tidak ditemukan defect)

1. **Cakupan `requireAdmin`** — seluruh `/api/admin/*` (`stats`, `orders`, `licenses` GET/POST, `bind`, `revoke`, `settle`, `ledger`, `usage`, `settings` GET/PATCH, `notifications` list/read/read-all) memanggil `requireAdmin` sebelum membaca body/state (`server.js:450-1163`); fail-closed saat `ADMIN_TOKEN` kosong kecuali `NODE_ENV=test|development` eksplisit (`server.js:1283-1292`, PM2 memaksa `production`). Header dibandingkan penuh `Bearer <token>`, bukan substring.
2. **IDOR customer** — pola konsisten "saring berdasarkan kepemilikan, samakan respons tak-ditemukan": order get/cancel/receipt (`server.js:1014-1080`, 404 untuk milik orang lain), token recovery (`server.js:990-1009`, sengaja 404 bukan 403), ledger & notifications & licenses selalu difilter `account.id` sesi (`server.js:780-811,907-938,973-988`), admin ledger adalah satu-satunya tampilan lintas-akun dan ber-admin-gate. Tidak ada endpoint yang menerima `accountId`/`licenseId` dari body untuk otorisasi (order create menurunkan `accountId` dari sesi, `server.js:1124-1130`; gateway mengabaikan identitas kiriman klien, `gateway.js:64-68`).
3. **Input validation pada mutasi state** — order create menolak `amount`/`description` dari body secara eksplisit dan mewajibkan plan aktif non-`custom` berharga > 0 dari katalog server (`server.js:1133-1152`); penerbitan admin menyelesaikan entitlement server-side dan mengabaikan `features/expiresInDays` body (`server.js:122-140,494-505`); settings divalidasi ketat (section tak dikenal ditolak, plans terduplikasi ditolak, kuota/model divalidasi, `settings.js:325-417`); gateway memvalidasi messages (peran, 1 system di depan, plafon byte), model ≤120 char, `maxTokens` ter-plafon, `requestId` ber-pola (`gateway.js:254-279,96-101,72-74`); body dibatasi 64 KB dengan penolakan eksplisit (`server.js:1294-1319`); segmen path di-decode aman terhadap URIError (`server.js:63-70` — regresi yang dulu berupa unhandled rejection kini 400).
4. **Payment/license integrity (di luar yang sudah dinyatakan selesai)** — settlement mengambil entitlement dari katalog saat settle, bukan nilai checkout basi (`paymentService.js:84-97`); kegagalan issue membiarkan order `PENDING` agar dapat di-retry (`paymentService.js:81-83`); settle admin memakai verifikasi upstream + cek jumlah yang sama dengan webhook (`server.js:1099-1118`, `amountMatchesOrder` fail-closed pada jumlah absen, `server.js:72-77`); receipt memerlukan order `PAID` + lisensi tertaut milik akun yang sama + capability (`server.js:1036-1064`).
5. **Response customer tidak membocorkan metadata internal** — `sanitizeLicense` tidak pernah menyertakan `grouterApiKey` dan hanya menyertakan token pada jalur owner yang disengaja (`server.js:1233-1248`); `sanitizeOrder` memisahkan QR/signature khusus-pemilik dari listing admin (`server.js:1250-1281`); `/api/resolve` tidak lagi mengembalikan apiKey apa pun (D-021, `server.js:524-552`); `/api/admin/usage` mengakui dimensi infrastruktur tanpa menyamar sebagai kuota pelanggan (`server.js:667-686`); admin settings termasking dengan keep-on-mask round-trip (`settings.js:423-446`); ledger customer membuang `answer/accountId/errorStatus` internal (`server.js:923-935`). Health/config hanya boolean & nama publik (`server.js:690-741`).
6. **Error handling umum** — tidak ada stack trace ke klien di jalur mana pun yang diperiksa; kegagalan validasi lisensi generik (403 tanpa oracle alasan di `/api/resolve` & heartbeat, kontras dengan `error` spesifik yang hanya membedakan kedaluwarsa — diterima); mailer membersihkan URL & rahasia dari pesan error (`mail.js:33-40`, `store.js:26-29`); log webhook hanya orderId + status klaim + outcome (`server.js:1177`); log reset password hanya email + status (`auth.js:189-197`). Pengecualian satu-satunya adalah A-09.
7. **Session/expiry dasar** — Better Auth: reset token 1 jam + revokasi semua sesi saat reset (`auth.js:192-197`), rate-limit auth aktif dengan custom rule yang terdokumentasi (`auth.js:204-212`), `trustedOrigins` eksplisit tanpa wildcard, cookie lintas subdomain opt-in eksplisit (`auth.js:124,232-234`), IP klien dari header tepercaya untuk rate-limit auth (`auth.js:217-223`). Lisensi: `exp` diperiksa validator, revokasi diperiksa ulang server-side di resolve/heartbeat/gateway terhadap store (bukan hanya tanda tangan), lisensi tanpa record store ditolak gateway sebagai revoked (`gateway.js:84-87`).
8. **Path traversal statis** — `/app/` backend dan `/assets/`+`/app/` frontendServer sama-sama resolve + cek containment + `isFile()` sebelum membaca (`server.js:413-439`, `frontendServer.js:138-180,192-217`); tidak ada penyajian direktori data/store melalui rute statis mana pun.
9. **Konkurensi event-loop yang disengaja** — reservasi kuota gateway adalah read-then-write sinkron tanpa `await` di antaranya (`gateway.js:198-208`), klaim email notifikasi sinkron sebelum `await` provider (di luar scope audit ulang — tidak ditemukan defect baru), scheduler notifikasi mempunyai overlap-guard (`notifications.js:517,525`).
10. **Rate limiting yang ada bekerja untuk sasarannya** — resolve/heartbeat/webhook/chat masuk `RATE_LIMITS` (kekurangan cakupannya adalah A-04/A-05, bukan ketiadaan total); auth mendapat limiter Better Auth + sentinel credential-stuffing.

- Audit read-only: tidak ada boot server dengan `DATA_FILE` default, tidak ada mutasi data prod, tidak ada instalasi paket. Probe runtime hanya pada store temp `/tmp` (dihapus sesudahnya) untuk A-01 & A-13.

Frontend React secara umum, plugin/host-app, dan gRouter upstream tidak diaudit.
