# Authoring developer-defined read-only skills

This guide describes the v1 skill contract used by `@grouter/copilot`. Skills are application code written and registered by a developer; they are not generated by the model. The runtime only executes registered skills and rejects mutating skills.

## Contract at a glance

A skill is a plain object with:

```js
export default {
  name: 'orders-summary',
  description: 'Read-only summary of orders for one customer.',
  intent: {
    phrases: ['order summary', 'ringkasan pesanan'],
    synonyms: ['orders', 'pesanan'],
  },
  parameters: {
    type: 'object',
    properties: {
      customerId: { type: 'string', description: 'Host-defined customer ID' },
    },
    required: ['customerId'],
  },
  readOnly: true,
  async run({ customerId }, ctx) {
    // Call a developer-owned, allow-listed data adapter here.
    return {
      data: { customerId, totalOrders: 0, totalValue: 0, orders: [] },
      sources: [{ label: 'orders summary (developer data adapter)' }],
    };
  },
};
```

Required fields are `name`, `description`, `parameters`, `readOnly`, and `run`. `readOnly` must be exactly `true`. The registry rejects execution when it is false or missing. The shallow argument validator supports JSON Schema `type`, `required`, `properties`, and `enum` checks.

## Safe authoring rules

1. **Keep the skill developer-defined.** Register a reviewed module in the host application. Do not let a model create or alter a skill, data source, URL, SQL statement, table name, or query plan.
2. **Make the data boundary explicit.** Use a fixed, allow-listed adapter such as `ctx.data` in a fixture or a host function with a fixed query. Do not accept raw SQL, URLs, collection names, or arbitrary field paths as model-controlled parameters.
3. **Read only.** Do not call `insert`, `update`, `delete`, `writeFile`, mutation HTTP methods, or equivalent side effects from `run`. A proposal is still read-only only when applying it happens outside the skill after explicit application logic and confirmation.
4. **Declare narrow parameters.** Require identifiers and bounded filters. Use enums and fixed limits where possible. Reject missing or invalid arguments before touching the data adapter.
5. **Return bounded, useful data.** Select only fields needed for the answer, cap result sizes, and avoid returning full records by default.
6. **Describe sources without credentials.** Sources should be stable labels such as `orders summary (developer data adapter)`, not connection strings, bearer tokens, API keys, SQL, or user secrets. The runtime redacts restricted keys and secret-shaped strings before model context is built, but skills should not return secrets in the first place.
7. **Treat host data as untrusted.** The model may see skill output, so avoid putting instructions, credentials, internal URLs, or unrestricted notes in the returned data. Context building applies redaction and byte/row limits; test the final shape as well as the skill itself.
8. **Fail closed.** If the fixed adapter is unavailable or the requested record is not found, return a bounded not-found result or throw; do not widen access or fall back to an unrestricted query.
9. **Do not make production claims from fixtures.** Example data is synthetic and local. Name fixtures as fixtures and keep credentials, real endpoints, and production identifiers out of the repository.

## CRM/POS shape

The repository's Mini CRM contract defines customers, leads, deals, and activities. A POS extension should use a similarly explicit host-owned shape, for example:

```js
{
  customerId: 'cus_fixture_001',
  orders: [
    { id: 'ord_fixture_001', outletId: 'outlet_fixture_001', total: 125000, status: 'paid' }
  ]
}
```

The sample at [`examples/skill-fixtures/crm-pos-read-only.js`](../examples/skill-fixtures/crm-pos-read-only.js) is synthetic. It reads only the `ctx.data.crmPos` object supplied by the test/host, returns an order summary, and exposes no write path. It is not connected to a CRM, POS, database, or production endpoint.

## Intent metadata

Use `intent.phrases` for deliberate multi-word requests and `intent.synonyms` for reviewed vocabulary. Intent metadata is only a routing hint; it does not grant access and cannot bypass registration, argument validation, read-only enforcement, or context limits. Ambiguous matches remain unresolved.

Keep entries short and bounded. Do not place user input, secrets, SQL, URLs, or arbitrary generated text in intent metadata.

## Testing checklist

For every skill, test:

- registration and required contract fields;
- explicit and natural-language routing, including an ambiguous request;
- missing, wrong-type, and invalid-enum arguments;
- not-found and empty-data behavior;
- output bounds and stable source labels;
- no mutation calls or mutation-shaped parameters;
- secret-shaped fields are absent from the skill output, and context redaction still holds for untrusted fixture data;
- deterministic synthetic data only, with no network or provider credentials.

Run the repository tests with `npm test`. The focused fixture test can be run with:

```bash
node --test test/crm-pos-fixture.test.js
```

This guide and the fixture document the current v1 contract; they do not add runtime behavior or imply that a production CRM/POS integration exists.
